Inside Real-Time Bidding
a lightweight walkthrough

Every time a page loads, an invisible auction fires, finishes, and delivers an ad — all before your eye reaches the headline. This page deconstructs how that happens, and how you can prototype the whole pipeline with a message broker, a cache, and a few small services.

01 · The Cast

Who's in the room when an ad is sold?

RTB is a marketplace. Four roles show up to every single impression.

📰

Publisher

Owns the page and the ad slot. Announces: “I have one impression, floor price $0.50 — who wants it?”

🔀

Exchange / Broker

The neutral middle. Broadcasts the opportunity to every connected buyer simultaneously and enforces the deadline.

🤖

Bidders (DSPs)

Automated buyers acting for advertisers. Each scores the impression against its campaigns and answers with a price — or silence.

📺

Ad Server

Once a winner is crowned, it fetches and renders the winning creative into the slot the user is looking at.

02 · The 100ms Auction

A full auction in the blink of an eye

Literally — a blink takes ~150ms. The auction is usually done first.

t = 0 ms

Page load → impression born

A user opens a page. The ad slot generates an impression with an ID, context, and a floor price.

t ≈ 10 ms

Broadcast

The exchange fans the bid request out to all subscribed bidders at once — one message in, N deliveries out.

t ≈ 10–70 ms

Bidders think fast

Each bidder evaluates targeting, budget, and predicted value, then fires back a bid. Miss the window and your bid simply doesn't exist.

t ≈ 80 ms

Auction closes

The auction engine buffers whatever arrived inside the window and picks the highest bid above the floor.

t ≈ 100 ms

Ad served

The winner is persisted to fast storage, and the ad server pulls the winning creative into the page.

03 · The Lightweight Build

You can prototype this with five small services

No planet-scale infrastructure needed to learn the mechanics. A broker gives you the fan-out for free: the publisher emits one message, every bidder gets its own copy, and nobody needs to know anyone's address.

📨

Message broker (e.g. RabbitMQ)

An impressions exchange fans each ad opportunity to per-bidder queues; a bids exchange funnels responses back. Publisher and bidders stay fully decoupled.

⚡

In-memory store (e.g. Redis)

The winner lands under a key like winners:{impressionId} — fast enough that the ad server can read it inside the same latency budget.

⏱️

Auction engine

Buffers bids for a fixed window, drops latecomers, picks the highest bid above the floor. Timeouts aren't an error path here — they're the design.

POST /impressions { "id": "imp-7431", "floor": 0.50 } → broker fans out → bids collected for the window → SET winners:imp-7431 { "bidder": "B", "price": 2.10 } → GET /winning-ad → creative rendered 🎉

05 · Takeaways

What the lightweight build teaches you

🧩

Decoupling scales

Adding a bidder is just binding a new queue to the exchange. No service redeploys, no address books — the same property that lets real exchanges host thousands of DSPs.

⏳

Deadlines shape design

The hard latency budget forces asynchronous fan-out, bounded buffering, and in-memory state. Every component exists because of the clock.

📈

Same shape at scale

Production systems swap in globally distributed exchanges, OpenRTB 2.6 JSON on the wire, and ML-driven bid pricing — but the request → fan-out → auction → serve skeleton is identical.
